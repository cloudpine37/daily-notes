# 读代码容易，读到「为什么」很难

最近开始每天读一个公开仓库、写一篇摘要。坚持了几天，最深的体会不是「学到了多少新东西」，而是发现一件反直觉的事：代码本身是最好读的部分，真正难读的是藏在代码背后的「为什么」。

一个功能，有人用十行写完，有人用一百行写完。十行未必精巧，一百行未必冗余——差别全在作者心里装着的那个「为什么」。是为了性能？为了可维护？为了向后兼容？还是单纯没想到？README 会热情地告诉你「这是什么」，却很少解释「为什么这么做」；而「为什么」往往散落在 commit message 里、在 issue 的争论里、在一个看起来多余的空判断里。

这周读到的一个细节让我记了很久：某个 CLI 工具在解析参数时，宁可自己写一段状态机，也不调用现成的库。第一反应是「造轮子」，翻完提交历史才发现，作者在 issue 里解释过——那个库在 Windows 上处理非 ASCII 参数时会把编码搞坏，而他们的用户有一半在 Windows。这段看起来「多余」的代码，其实是踩过坑之后留下的疤。

由此想到自己写的代码：有多少段，是别人读起来也会在心里问一句「为什么」的？我是不是也该在那些看似奇怪的地方，留下一点说明，而不是指望后人——包括三个月后的自己——能心领神会。

读开源的意义大概就在这里：不是为了收集 API，而是借别人的代码，看清自己那些说不出口的假设。下周继续。
