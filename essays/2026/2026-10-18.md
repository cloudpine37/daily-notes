# 读代码这件事，到底在读什么

这一周，我每天会挑一个公开仓库，读它的 README 和几个关键文件，再写一篇摘要。做了几天之后，我慢慢意识到，这件事真正的难点从来不是"读"，而是"知道自己在读什么"。

README 是一个仓库的自我介绍：它想解决什么问题、怎么安装、怎么跑起来。但 README 写得再好，本质上也只是一种承诺，真正让承诺落地的是源码。同样是"支持流式输出"，有的项目二十行就写得清清楚楚，有的项目却要绕三个文件和一个状态机才勉强说圆。读源码的时候，这种差别会直接暴露出来——它不一定是性能的差别，更多是思考清晰度的差别。

更让我意外的是 commit message。不少优秀项目的提交历史读起来像一本简短的日记：为什么改、改了哪里、有什么副作用，一条条清楚明白。而另一些项目明明代码写得不错，提交记录里却只有"fix""update"两个词反复出现。前者让后来的人——包括未来的自己——能顺着历史读懂来龙去脉，后者则把所有上下文都锁在当事人的脑子里，时间一长就成了无头案。

这让我重新理解了"可维护"三个字。它不只是代码结构的事，还包括文档、命名、提交信息这些看起来琐碎的东西。一个陌生人在十分钟内能不能看懂你的项目、能不能放心地改一行代码，才是开源协作真正在考验的东西。

技术栈会过时，工具链会换代，但"把一件事讲清楚"的能力不会过时。读代码读到最后，读的其实是作者怎么思考、怎么表达、怎么替别人着想。这一点，比任何具体的 API 都更值得记下来。
