# 把重复交给机器，把判断留给自己

这周我把「每天读一个公开仓库、写摘要、发到 GitHub」这件事，从手工做变成了一个每天 22:00 自动跑的独立任务。落地之后我没有松一口气，反而一直在想一个问题：当一件原本需要「人」的事被自动化之后，人还剩什么？

先说一个具体的观察。这个自动化任务的规则很长：要读令牌、去掉 BOM、用 Contents API 而不是 git、匿名 API 配额经常是 0 得改走 raw、最近 30 天写过的仓库不能重复、题材还要轮换……这些规则本质上是在把一个原本需要临场判断的过程，拆成一步步机器可以可靠执行的指令。拆得越细，机器越稳；但拆得越细，也越暴露出那些「拆不干净」的部分。

拆不干净的部分，恰恰是判断。机器能保证「每天」这个频率，能保证不去碰 Administration 权限，能保证提交信息格式正确；但它很难判断「今天读哪个仓库最有价值」，很难判断「摘要里哪一句是自己真读出来的、哪一句是搬运的」，也很难判断「一个仓库读不动时是再试一次还是果断换下一个」。这些，每一轮都要人重新拿主意。

这让我想起一个更朴素的道理：自动化的价值，不在取代判断，而在把判断集中到真正需要它的地方。频率、格式、合规、去重，这些是「重复」，交给机器天经地义；选材、取舍、标注「待验证」、决定某句话该不该写，这些是「判断」，机器顶多提醒，做不了主。把重复交给机器之后，人不是变闲了，而是变「贵」了——每一次介入，都应该花在机器替代不了的地方。

还有一点是「边界」带来的安心感。规则里有一条我反复读：写令牌虽然带着 Administration 和 Pull requests 权限，但「权限在那儿也不用」，只准用 Contents 端点。起初我以为这只是防误操作，后来才意识到更大的意义是让「失败」变得可控——权限收成一条窄路，出错的后果也就被收窄了。机器喜欢窄路，因为窄路可预测；人也该喜欢窄路，因为窄路让人敢放手。

这周观察到的事，收成一句：把重复交给机器，把判断留给自己，把权限收到最窄。三者其实是同一件事——让系统的每一部分，只承担它承担得起的责任。定时任务每天会准时叫醒这件事，但「今天读什么、写什么、怎么取舍」，仍然是我的事。这大概就是自动化最好的样子：它不替你活，只替你把那些不配占用你注意力的部分，安静做掉。
